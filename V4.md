# v4 ideas

Collected directions for a future major. None of these are committed; each section notes the motivation, a possible API shape, and the open questions.

## Declarative API: `useFaviconHref`

**Motivation.** React 19 hoists `<link>` rendered anywhere in the tree into `<head>` (see the README's [React 19 and head elements](README.md#react-19-and-head-elements)). The current hook mutates a link element out-of-band, which works but sits awkwardly next to a React-rendered icon link: a re-render with a different `href` prop silently overwrites the hook's drawing. A declarative variant dissolves that conflict — React owns the element end-to-end.

**Sketch.**

```tsx
function Notifications({ count }) {
  const href = useFaviconHref(drawTextBubble, {
    base: "/favicon.svg",
    label: String(count),
  });

  return <link rel="icon" href={href} />;
}
```

- Returns a `data:` URI string, recomputed when the callback or options change.
- No DOM mutation, no restore semantics needed — unmounting the `<link>` *is* the restore.
- SSR-friendly: the first render can return `base` (or `""`) and fill in the drawn URI after hydration.

**Open questions.**

- The imperative hook reads the *current* favicon as the background; a declarative version can't (it owns the favicon). An explicit `base` option is the honest replacement — is that acceptable, or does it lose the main draw-on-whatever-is-there appeal?
- Drawing is async (image decode), so the returned href changes one render late. Fine in practice, but the docs would need to say so.
- Does this replace `useFavicon` in v4 or ship alongside it? Alongside seems right: the imperative hook remains the only way to composite onto a framework-declared favicon you don't control.

## WebGL / WebGPU rendering

**Motivation.** Anything you can render in realtime graphics — shaders, 3D spinners, generative art — could be a favicon. Both APIs render to a canvas, and `drawOnFavicon` is already async, so this is a natural extension rather than a new architecture.

**Sketch.** A `context` option that changes what the callback receives:

```tsx
// today (implicit "2d")
drawOnFavicon((ctx, size, options) => { ... });

// v4
drawOnFavicon((gl, size, options) => { ... }, { context: "webgl2" });
drawOnFavicon(async ({ device, context }, size, options) => { ... }, { context: "webgpu" });
```

Typing: overload `drawOnFavicon` on the `context` discriminant so the callback's first parameter is `CanvasRenderingContext2D`, `WebGL2RenderingContext`, or a WebGPU bundle respectively.

**Technical notes.**

- **Compositing.** Keep the draw-on-top-of-current-favicon semantics by rendering GL/GPU output to its own canvas, then `drawImage`-ing that onto the existing 2D pipeline (background favicon first, GL canvas on top). Users then don't need to load the favicon as a texture to preserve it.
- **WebGL readback.** `toDataURL()` on a WebGL canvas only works reliably with `preserveDrawingBuffer: true` or when read in the same task as the draw. Compositing onto the 2D canvas in the same task sidesteps the flag and its performance cost.
- **WebGPU.** `navigator.gpu.requestAdapter()`/`requestDevice()` are async (already fine), the canvas context needs `configure({ device, format })`, and readback happens after the queue submits. Feature-detect and fail with a clear error — WebGPU is still not universal.
- **Alpha.** Favicon compositing needs transparent backgrounds; both contexts must be created with alpha enabled.

**Open questions.**

- One generic `context` option vs. separate `drawOnFaviconGL` / `drawOnFaviconGPU` entry points (better for tree-shaking the WebGPU plumbing)?
- Should the library manage device/context lifecycle across calls (caching the device) or create per-call?

## Animation helper

**Motivation.** Progress spinners and pulsing badges need a render loop; today users would hand-roll `requestAnimationFrame` around `drawOnFavicon`.

**Sketch.**

```tsx
const stop = animateFavicon((ctx, size, t) => {
  // t: elapsed ms
}, { fps: 4 });
```

**Notes.** Browsers throttle favicon updates and each frame is a full canvas → data-URI → link mutation cycle, so the helper should default to a low frame rate (2–5 fps) and pause when the tab is hidden — which is also when favicon animation matters most, so `visibilitychange` handling is the interesting design problem, not the loop.

## Dark-mode aware favicons

**Motivation.** SVG favicons can embed `prefers-color-scheme` media queries ([write-up](https://blog.tomayac.com/2019/09/21/prefers-color-scheme-in-svg-favicons-for-dark-mode-icons/)). The hook could offer first-class support instead of leaving it to hand-written SVG.

**Sketch.** `emojiSvg` could accept a `{ light, dark }` pair and emit a single SVG with an embedded `<style>@media (prefers-color-scheme: dark) { ... }</style>`. Canvas-drawn favicons can't respond to scheme changes after rasterization, so this only applies to the SVG path — worth stating clearly.

## Smaller items

- Re-render the drawn favicon when the underlying original changes (watch the link with a `MutationObserver` instead of only re-finding on the next call).
- `OffscreenCanvas` + worker rendering for heavy draw callbacks, falling back to the current path where unsupported.
- Multi-size output: generate and manage several `sizes` variants from one draw call.
